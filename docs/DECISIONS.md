- **2026-07-27 · NONET-25: Record, and two figures the data cannot honestly supply.** Every number here is derived from the solve rows and none is stored, for the reason NONET-13 gives — a counter beside the rows drifts the first time a solve arrives out of order, which is exactly what signing in does. So Record cannot disagree with Home or with the result screen, because all three read the same two functions. **Two figures `copy.md` asks for are not rendered, and neither is faked.** The hint rate, "0.4 per puzzle", is **not derivable**: `usedHint` is a boolean on the guest record *and* on the `solves` table, so the count per puzzle is stored nowhere. Migrating the schema for a vanity figure is disproportionate, so the page reports the **share of assisted solves**, which says the same thing from the data that exists. And the completion strip's summary counts failures, which **nothing records**: a locked board deliberately writes no `solves` row (NONET-17) and attempts are stored per puzzle without a date, so a day that was attempted and lost is indistinguishable from one never opened. The strip says solved and unplayed and does not guess. **The mistake-free share counts only checked solves.** A purist run has no tally at all, so counting it as clean would inflate the figure with runs that were never measured — the denominator is what makes that statistic honest. **The headline spells its number** to ninety-nine and then falls back to digits, because "One hundred and seventeen days, unbroken" is a mouthful where the figure is the point. **A defect found on screen, not by a test:** the strip read "1 solved" while the stat grid beside it read 22. `yearGrid` was checking the epoch before the solves, so every day before `PUZZLE_EPOCH` drew as "no edition existed" even where a solve was recorded on it. A solve is evidence that an edition existed, so it now outranks the epoch — while a *future* date still wins outright, since it can only come from a wrong clock and the streak ignores it for the same reason (NONET-9). Two figures on the same page contradicting each other is worse than either being slightly wrong, and only looking at them together shows it. Thirty-four tests. Rationale: this page is nothing but claims about a player's history, so the two figures it cannot support are the ones worth being explicit about.

- **2026-07-27 · NONET-24: Settings, and four columns that finally do something.** The store, the columns and the sync shape have existed since NONET-17; what was missing was anywhere to change them, and **four of the seven were being stored, synced and read by no component at all** (OPEN-QUESTIONS #2). Columns existing is what made that look finished when it was not, which is why it was flagged rather than left to be discovered. **There is no Save button**, because there is nothing to batch: each setting is independent and the copy promises "every change applies to the next cell you touch", so each writes immediately. **Theme is written twice, deliberately** — into the settings blob so it syncs with everything else, and under its own key because a blocking inline script reads it before first paint to stop an explicit light choice flashing dark on a dark device, and that script cannot parse a JSON object (NONET-11). The two have to move together or the flash comes back. **Auto-advance is an engine rule, not React state.** Where the selection lands after a placement is part of how the board plays, and reimplementing it in a component is exactly the split NONET-8 exists to prevent — so it is a `SessionOptions` flag and a branch in `placeDigit`, with six tests. Three of those pin things that are not obvious: it fires **only on a correct placement**, because a wrong digit has to be fixed and moving the player off the cell they just got wrong is the opposite of helpful; **only in cell-first**, since in digit-first the digit stays loaded and the player taps every cell that takes it, so advancing would fight the gesture rather than help it; and it **wraps** rather than stopping at cell 80, or a player filling the grid out of order is stranded at the end with gaps behind them. The Settings control is shown *inert* in digit-first rather than hidden, because a control that vanishes reads as a bug while one that is visibly unavailable explains itself. **Hiding the timer does not stop it**, which the copy states and a test now pins: the readout goes and `elapsedMs` keeps arriving, keeps being saved, and is shown at the end. Rationale: four settings that persist and sync while nothing reads them is worse than four settings that do not exist, because the first looks done.

- **2026-07-27 · NONET-23: Home, and two actions deliberately not offered.** **Which of six things Home shows is decided in `lib/home.ts`, not in the component.** Every branch has different copy and two have different actions, so wrong precedence is a screen offering the wrong thing rather than one that looks slightly off — and precedence is stated rather than implied. **Solved beats a saved board**: finishing clears the autosave, but a stale one can arrive from another device, and offering "resume" on a solved puzzle would let it be replayed for a second set of stats. That is the rule the merge already applies (NONET-18) and the two have to agree. Failed sits above in-progress for the same reason. **`first-visit` is not "today unplayed".** A player with no history at all gets the invitation and **no streak band**, because a band reading zero is a worse greeting than none; a player returning after a lapse still gets it, because it is their record rather than a greeting. **`spent` is not in `copy.md`**, which only ever drew one failed state — there is no third attempt (NONET-17), so it keeps the message and loses the action, exactly as the pause veil does. **Two things the export asks for and this does not render, both marked where they sit.** The practice rows carry a median time per band; there is no solve data to derive one from, and a plausible-looking median is a fabricated statistic in a product whose streak model rests on not overstating things. Record derives real ones once there are solves. And the solved hero's secondary action, "Replay, unscored", is absent because **replay mode does not exist** — `solves.kind` can hold `'replay'` and nothing writes it, so the link would land on the ordinary daily board and record a second *scored* solve for a puzzle already banked. A missing action beats one that quietly corrupts the stats. **`/board` now takes a puzzle in the URL**, which is what makes practice playable at all: `pickPractice` had been written and tested since NONET-17 with no caller, and the board route was hardcoded to the daily. An unparseable ref falls back to the daily rather than erroring, because there is always a puzzle to play. **The abandon confirm is the only control on Home that destroys something** — practice boards are not kept, so starting a second one discards the first rather than setting it aside — and it is the only place the product asks before acting. Verified in a browser at 1440 and 375: the scrim covers the viewport exactly, focus lands on the first action, Escape keeps the board and returns focus to the row that opened it. **The hero splits 1fr / 500px on the rail** per `layout.md`; built single-column first and it read as an unfinished page with an empty right half, which is what looking at it caught. Eighteen tests, and the whole practice loop driven by hand: pick a band, deal seed 837, place a digit, return to a resume strip reading "Hard, 31 of 81 placed", discard it, and watch the new board replace the old autosave. Rationale: the two omissions here are both cases where the design drew something the data cannot honestly support yet, and drawing it anyway would have been the first dishonest thing in the product.

- **2026-07-27 · NONET-21: A six-digit code, reversing the magic link in NONET-18.** **The argument is specific to this product, not a general preference.** The only thing an account does in Nonet is carry a streak between devices — everything is playable signed out — so the moment somebody signs in is very often on their *second* device, and that is precisely where a link is worst. The link opens in whichever browser the mail client owns rather than the tab the player started in, so they authenticate somewhere they were not playing and the original tab is still signed out. Mail gateways that prefetch links also spend the single-use token before any human clicks it, which fails in a way that looks like the product being broken. A code has neither failure mode: the player stays where they are and types six digits. **Rejected: passwords**, which are friction at exactly the wrong moment and oblige a reset flow — and a reset flow *is* a magic link, so the link would have come back through the side door along with a stored credential, to protect a sudoku streak. **Rejected: offering both**, which doubles the copy and the surface and makes the choice itself the friction, in a product this spare. **Noted for v2: passkeys**, which are the genuinely modern answer, but Supabase supports WebAuthn only as a second factor and not as a primary one, so it means hand-rolling the ceremony against a custom endpoint. **The template is the flow.** Supabase decides whether it sends a code or a link purely from what the email template references — `{{ .Token }}` or `{{ .ConfirmationURL }}` — so the entire sign-in method lives in an HTML file, and reverting that file silently reverts the flow with nothing failing until somebody reads a real email. Recorded in `config.toml` next to the setting, because it is the least discoverable dependency in the product. **And it is stored twice:** the hosted project keeps its own copy of every template and does not read `config.toml`, so local and remote must both be changed or local sends a code and production sends a link. **The merge marker moved to the client.** `merged=1` is what raises the post-sign-in summary, and it was added by the callback route — which a code never touches. Without adding it after `verifyOtp`, signing in would still work and would silently stop carrying a guest's history across, which is the one failure here nobody would notice until their streak was gone. **`safeRedirect` still guards `next`**, now on a client navigation rather than a server one; the session is live by that line, so the whitelist and its twenty-three tests matter exactly as much as they did. **The callback route stays**, unused by this flow: it is already written and hardened, an email-change confirmation still arrives as a link, and a dead route that works beats deleting one and discovering why later. Thirteen tests, including that no `emailRedirectTo` is sent, that the field is typed `one-time-code` so iOS offers the code it has just received, and that a wrong code keeps the player on the step rather than throwing them back to the start. **Diverges from `copy.md`** — "We send a link, you click it" and "I clicked the link" are now a code and a Sign in button. The export is a transcription of the prototype and stays as it is; this entry is the record. **Not yet verified in a browser end to end**, because that needs a live project; the first step is confirmed on screen and the code step is unit-tested only. Rationale: the flow that was verified working in NONET-18 was verified on one device, and the second device is the entire reason the feature exists.

- **2026-07-27 · NONET-19: The drawer, and a silent gap in the Tailwind bridge.** **`--spacing: initial` was too blunt, and it failed silently.** NONET-11 cleared the numeric spacing scale so `p-4` could not exist and every measurement had to come from the 12-step scale. The general lesson is worth more than the fix: **a Tailwind utility that is not generated is indistinguishable from one that has no effect**, so clearing a namespace needs the exceptions thought through, and overlays need looking at rather than reasoning about. **The drawer is a full-frame overlay, not a side sheet** — an editorial contents page (DESIGN.md), with the trigger drawn as three stacked hairlines, the product's own rule language rather than a borrowed hamburger, plus a mono MENU label so it is named and not only drawn. **Everything below the visuals is new work**: the prototype's accessibility tree comes back empty, so `role="dialog"`, `aria-modal`, `aria-expanded`, the focus trap, Escape handling and the scroll lock are the build's to write. - **2026-07-27 · NONET-18: Sign-in, and the merge as a pure function.** **The rules are three pure functions over two lists**, in `merge.ts`, with sixteen tests — and the plumbing that talks to Supabase is somewhere else entirely. This is the only place in the product where being wrong destroys a player's history rather than looking wrong, and no design mock can express any of it, so it had to be the part that is provable without a database. Server wins for completed solves; latest wins for a puzzle in progress; ties break towards the server, so there is one direction to remember rather than three. **Three rules that only became visible by writing the tests.** A first attempt and a retry are *different runs*, not a conflict, so both survive — keying on the puzzle alone would have silently dropped one. **A solved puzzle beats any board for it**: a guest board left open on another device is stale the moment the solve lands, and resuming into it would let a finished puzzle be replayed for a second set of stats. And the merge is **idempotent** — merging its own output uploads nothing — because a player signing in twice on one device should not re-send their history, and every write is an upsert so a half-finished sync is retried by simply signing in again. **Settings are not merged, they are chosen.** There is no honest way to combine two sets of preferences. The account wins, because that is what "sign in and they follow you" means — except on the first sign-in, where the profile holds nothing but column defaults and the guest's are the only real choices in play. Taking the server there would silently reset everything a player had chosen, at exactly the moment they would notice and have no idea why. Recognised by `settings_synced_at`, because comparing columns to their defaults cannot tell a fresh profile from one whose owner likes the defaults. **The redirect is a whitelist, not a pattern**, per the standing rule. An open redirect in an auth callback fires with a freshly-minted session in hand. Twenty-three tests, every one of them a case a clever string check gets wrong at least sometimes — `//host`, a backslash, an encoded slash, an absolute URL ending in a known path. `/board` is deliberately not a target: it needs a puzzle, and "sign in, land on a board you did not choose" is not a flow. **Two defects found by running it, not by reading it.** `additional_redirect_urls` allowlisted only the origin, and Supabase validates `emailRedirectTo` against that list and **silently falls back to `site_url`** when it does not match — so a missing entry does not error, every magic link just goes to the wrong page. And the guest's in-progress board was being looked up by the *server's* ref, which meant a board the account had never seen — precisely the case where the guest's should win — could never be found, let alone uploaded. **`otp_expiry` is 900 seconds** because the Auth copy says "It expires in fifteen minutes" and the default is an hour: a stated expiry the product does not keep is a small lie in the one flow where a player is deciding whether to trust it with their history. **The proxy guards nothing.** It refreshes the session and that is all — every route is playable signed out, so there is no page to gate, and a proxy that redirected would be the one thing standing between a guest and their puzzle. Verified end to end against the local stack: form, magic link, PKCE exchange, three solves uploaded, settings pushed as the guest's, the in-progress daily uploaded once its edition existed, and a second run adding nothing. Rationale: the merge is the one feature here where "it looked right" is worth nothing, so the rules are tested in isolation and the wiring was watched doing it for real.

- **2026-07-27 · NONET-16: The daily, the bank, and one import convention for three resolvers.** **`packages/engine` now names `.ts` on every relative import, and that is a reversal of NONET-11.** Turbopack cannot resolve a `.js` specifier to a `.ts` file, which is why extensions were stripped; Deno cannot resolve an extensionless one, which is why they are back. `.ts` is the single form all three resolvers accept — verified, not assumed: the same engine source now runs under vitest, under Turbopack's production build, and under the edge runtime, and Deno returns byte-identical output to Node for the same date. The convention is scoped to the engine, because the engine is the only package that crosses the Deno boundary; `apps/web` stays extensionless behind its `@/` alias. A rule with a reason beats a rule for symmetry. It needs `allowImportingTsExtensions`, which is safe here because every package is `noEmit`. **The daily's identity lives in the engine.** `dailySeed`, `dailyDifficulty` and `puzzleNumber` are needed by both the browser and the publish job and they must agree exactly, so there is one implementation. The seed is FNV-1a over the ISO date — chosen for being a fixed published algorithm nobody will be tempted to improve — and **the values are pinned by test**, so a refactor that changes the hash fails rather than silently re-minting the entire archive. Weekday is read in UTC, because the edition's day is a property of the edition; a player's own timezone decides their *streak* day, which is a different question (NONET-9). **`PUZZLE_EPOCH` is 2026-07-27, so the first edition is No. 1.** The prototype shows "No. 1247", which would have been a vanity offset pretending the product had been running for three years; rejected, on the grounds that a product whose entire streak model rests on not overstating things should not open by overstating its own age. Now frozen — moving it renumbers editions people have already shared. **Idempotency is in SQL, not in the function.** `publish_daily()` is one `on conflict` against the partial unique index, returning the existing id on a repeat, so a cron that fires twice, a retry after a timeout and a manual backfill are all safe by the same mechanism — and it is testable in pgTAP without running Deno. `published_at` is derived inside it as 00:05 UTC on the edition's own date, so no caller can publish early by asking. **Two defects the tests caught.** Revoking execute from `PUBLIC` left the function callable by `anon`: Supabase's default privileges grant execute on new functions to `anon` and `authenticated` *by name*, and a named grant survives a revoke from `PUBLIC`. The anon key ships in the client, so that was a stranger being able to mint editions. And `formatGrid` writes `.` for an empty cell while every grid column is constrained to digits — the insert failed outright, but the same mismatch was sitting unexercised in the autosave record, which is the `autosaves` row's shape. `formatGrid` now takes the empty character: `.` reads better in a fixture, `0` is what persistence wants. **A local-stack landmine worth knowing:** on PostgreSQL 17.6 arm64 in the Supabase image, calling *any* function the current role lacks EXECUTE on **segfaults the backend** — security definer or not, trivial body or not. Permission tests therefore assert `has_function_privilege` rather than expecting a `42501`, which is the more direct claim anyway. Table-level denials raise normally. **The practice bank is 1000 per band, 4000 rows, 790 KB, 35 seconds**, generated from seeds `1..1000` — checked in but reproducible byte-for-byte, and any single puzzle rebuildable from its band and seed. Loading it twice is a no-op. - **2026-07-27 · NONET-4: Difficulty is a weighted effort score (supersedes the rater in NONET-3).** NONET-3 rated by given count with the technique ceiling as an upward guard. That was measured and honest but it made the band labels weak: a ceiling is a maximum over the solve, so it discards *how much* hard work a puzzle takes, and the given-count axis meant "Expert" often just described a sparse grid that fell to singles. Replaced with a single number: **score = the summed weight of every step the human solver takes**, in naked singles (nakedSingle 1, hiddenSingle 2, nakedPair 5, hiddenPair 8, nakedTriple 10, pointingPair 12, boxLine 14, xWing 30, chain 50). Steps, not eliminations — one naked-pair step is one deduction a human made, not six. Because the solver is greedy cheapest-first the score measures the easiest available path, which is what a competent solver would find, and it stays deterministic. **Given count is no longer consulted**: it is already implicit, since a puzzle needs `81 - givens` placements and each costs at least a point, so a singles-only grid scores exactly `81 - givens`. That "scanning baseline" is what the bands are set against. **Bands** (calibrated over 500 digs per band): Easy < 47, Medium 47-57, Hard 58-82, Expert ≥ 83, against baselines of 43/47/51/57 — so Hard demands 7 points of technique beyond scanning and Expert 26. That margin is the whole point of the change. **The ceiling guard is gone** — the weights already price technique (one chain step is 50, enough to carry almost anything to Expert), and two axes meant two sources of truth. `TECHNIQUE_CEILINGS` survives only as the generator's dig bound. **The generator re-rolls** until the score lands in band, keeping the design given counts exact (38/34/30/24) at the cost of attempts: measured in-band rates per dig are Easy 97%, Medium 95%, Hard 42%, Expert 26%, so Expert needs about four digs; `MAX_ATTEMPTS` 40 puts failure near 4 in 100,000, and generation runs once a day. **Thresholds are calibrated, weights are judgement.** `scripts/calibrate.ts` is checked in and re-derives the floors, placing each at the percentile of its band's own distribution that leaves a target share qualifying (95% Easy/Medium, 40% Hard, 25% Expert) — deliberately *not* the best-separating threshold, because the four dig populations are separated mainly by their baselines and optimal separation just recovers given-count banding. The weights cannot be calibrated without human solve times, so the plan is to persist `score` on the `puzzles` row in Phase 3, then re-derive weights from real completion times and re-band the bank with a script. Consequence worth noting: the canonical Wikipedia grid (30 givens, singles-only) now rates Medium at 51 points, where the NONET-3 rater called it Hard. Rationale: the product promises four distinct difficulties, and a band that a player cannot feel the difference of is a label, not a difficulty.

- **2026-07-27 · NONET-3: Engine architecture (Phase 1).** `packages/engine` built test-first: pure TS, no runtime dependencies, vitest only. **Technique ladder** — nine techniques applied strictly cheapest-first: naked single, hidden single, naked pair, hidden pair, naked triple, pointing pair, box-line reduction, X-wing, chain (simple colouring). Naked triple is an addition to the order named in ROADMAP; it is cheap and stops Medium puzzles falling through to fish techniques. The order is load-bearing: because the solver always reaches for the cheapest applicable technique, the hardest technique a puzzle forces is a stable property of that puzzle, and the rater, the generator's dig bound and the hint ranking all read it. Reordering `TECHNIQUE_ORDER` re-rates the whole bank. Cell iteration is fixed and no technique uses randomness, so `analyse` is deterministic. **Difficulty rating — given count is the primary axis, technique ceiling can only raise the band.** This reverses the plan I opened with, and the reversal is data-driven: digging to the design given counts leaves a singles-only grid most of the time, even at 24 givens (24 of 30 sampled Expert-count grids had a ceiling of 2, and ranks 6-7 almost never appear as the hardest technique needed). Hardest-technique and given count are close to independent in this range, so requiring both to land in a window simultaneously made Expert generation fail outright for roughly 3% of seeds. A ceiling cannot define a band from below; it can only bound one from above. Bands: Easy 37+ givens / ceiling ≤ 2, Medium 33-36 / ≤ 5, Hard 27-32 / ≤ 7, Expert ≤ 26 / ≤ 9. A grid deduction cannot finish rates Expert. **Generator guarantees uniqueness by construction** — digging starts from a complete solution and clears a cell only if the grid still has exactly one solution afterwards, so a second solution can never appear; re-checked before the puzzle is returned. "Never requires a guess" holds the same way: a removal is only accepted if the human solver can still finish within the band's ceiling. Digging stops on reaching the target count, so puzzles are never sparser than the design asks, only occasionally denser when no further cell can be cleared. **No 180-degree symmetry** — symmetric digging removes cells in pairs and can only leave an odd given count, and all four design targets are even; the design rules symmetry out. **Undo/redo and mistakes live in the engine** as a pure session reducer, because "undo never uncounts a mistake and never restores a spent hint" is only testable where history, tally and hints sit together, and it keeps those rules out of React. History carries the grid and notes only; hints are burned into every stored snapshot so undo cannot lift one. Rationale: the engine is the one place these rules can be proven, and the two that are invisible in any screenshot — digit-first mistake containment and undo-versus-tally — are exactly the ones a UI would otherwise get wrong.

- **2026-07-27 · NONET-2: Full-surface design resolved (pre-code).** Eight review passes against the Claude Design full-surface build, grilled screen by screen. **Navigation:** Practice folded into Home — it was a nav destination duplicating an identical Home section, so nav is now Today · Archive · Record and there is no `/practice` route; the practice picker, resume band and abandon confirm all live on Home. **Board input:** two modes, cell-first (default) and digit-first, chosen in Settings and switchable on the board; long-press a pad key writes a note (four taps → two); `Shift`+digit is the keyboard equivalent; pad keys become non-interactive at zero remaining; auto-advance is a setting, off by default. **Digit-first mistake containment:** while a digit stays loaded, repeated wrong placements of that same digit count as one mistake — without this, three fast taps end a puzzle, a cliff that only exists because the mode is fast. This is an engine rule and needs a unit test. **Hint guard:** the first hint per puzzle confirms once (it is irreversible and forfeits the percentile); hints two and three go straight through. **Exiting a puzzle:** immersive board retained, but `CLOSE` replaced by a left-aligned back control labelled for its origin (`← TODAY` / `← ARCHIVE`) — "close" implied discard on an autosaved puzzle. **Archive vs Record:** they were one component serving two jobs; now Record is a non-interactive year heat strip (a month cannot show a 61-day run) and Archive is a navigable month grid carrying difficulty per cell plus a filter rail. **Guest→signed-in merge:** the rule already existed but had no surface; a post-sign-in summary now reports what merged, which run stands and which in-progress puzzle was kept — it reports, it never asks. **Responsive:** mobile drawer below 768px, single-row site header above it, board rail at 1100px+ and bottom control band below. **Tokens:** colour, type, space and motion all named on a dedicated Tokens screen in the prototype, which is the transcription source for `packages/design`. **Accessibility:** focus states designed visually (distinct from cell selection) in the prototype; real ARIA/semantics are the build's job, as the design runtime cannot express them. Rationale: the prototype is a pixel and behaviour reference for a from-scratch build, so quirks resolved here are quirks not baked into code.
